Read this before planning

The single most important architectural fact in this codebase: all data is synthetic, generated deterministically at module load, and the app has no database and no authentication. Every write (a lead, a moderation decision, a vendor reply, a listing-edit proposal) mutates an in-memory object and is lost on restart. Any enhancement that needs durable state starts with the repository swap described in section 15, not with a new page.

The three things worth knowing

  1. One module is the whole data layer. lib/data/repository.ts exposes 56 accessors and is the only thing any page or route imports. A swap to Prisma or Drizzle touches one file. This was deliberate and it holds: no page imports seed.ts.
  2. Mutable state lives on globalThis, and it must. Production Next.js instantiates a module once per route bundle, so a plain module-level array diverges: an API route writes and returns 201, and the page never shows it. This bug was real and was fixed in e44b3a6. Any new mutable store needs the same wrapper.
  3. The dataset is defined by its PRNG. lib/data/seed.ts keeps a private copy of the generator. Refactoring it onto the shared lib/procedural.ts PRNG would change every product, score and review, invalidating every number recorded in this report. Do not do it.

02What it is, and what is locked

The product definition and the decisions that are settled. Re-litigating these costs time; changing them is a product decision, not a bug fix.

In scope, shipped

  • Public catalogue: home, search, categories, product profiles, side-by-side comparison
  • Trust layer: verified-review labels, an explicit methodology page, disclosed synthetic data
  • Vendor portal: overview, enquiries, listings, reviews (pinned to one demo vendor)
  • Admin portal: dashboard, leads, moderation queue, SEO consistency gate
  • Write-back API: enquiries, lead status, moderation decisions, vendor replies, listing-edit proposals
  • Knowledge graph surface (/graph) from a pre-built Graphify artifact

Locked decisions, do not re-litigate

  • Light enterprise aesthetic only. Zinc-200 borders, single blue accent #2563EB. Dark mode, neon and glassmorphism were explicitly rejected.
  • All data is synthetic and disclosed as such. A DemoDataNotice sits in the root footer and both portal layouts. Keep it.
  • No authentication. The portals are pinned to DEMO_VENDOR_SLUG = "salesforce"; moderation records the literal actor "unauthenticated" rather than inventing an identity.
  • 1.5 MB initial-JS contract. 1,536 KB. Every route is measured against it.
  • No charting library. recharts is installed and imported nowhere; all charts are hand-rolled SVG. Do not add it.
Boundary that matters commercially

Vendors can propose copy (tagline, short description) but cannot edit anything that feeds the composite score: ratings, review counts, feature coverage. That boundary is documented on /vendor/products and enforced by the schema, not by the UI. Protecting it is the credibility of the whole product.

Consequence to plan around

/product/[slug] has generateStaticParams, but only for the featured, trending and top-per-category products. The rest render on demand. So a vendor reply is visible on most product profiles but would be stale on a prerendered one. If you make writes durable (section 15), decide deliberately whether product pages become force-dynamic or take an ISR revalidation path.

Heavy assets are JS-gated, never CSS-hidden

Two components carry weight that would blow the budget if it shipped unconditionally:

  • HeroScene dynamically imports three behind a viewport-width gate.
  • GraphFrame gates the 1.4 MB self-contained Graphify viewer behind the same pattern.

The gate runs inside an effect and renders nothing until it passes, so SSR and the first client render agree (no hydration mismatch). A CSS hide such as hidden sm:block would still download the asset, which is why it is not used.

04State, data flow and the singleton rule

The one bug class that has already bitten this codebase, and the rule that prevents it recurring.

The singleton rule

Production Next.js gives each route bundle its own module instance. A plain module-level binding is therefore created more than once, and an API route will happily mutate a copy no page ever reads. The symptom is distinctive and misleading: the write returns 201, the response body is correct, and the UI never changes.

This actually happened here

Discovered in the B4 cycle. dataset was module-scoped in the repository while leadStore, moderationLog, productDecisions and listingEdits were already wrapped. A vendor reply returned 201 and appeared on neither the portal nor the product page. It was only caught because the guard posted a unique marker and grepped the rendered HTML for it, rather than asserting on a static string.

The required pattern, used six times in the repository:

const globalForDataset = globalThis as unknown as { __dataset?: typeof seeded };
const dataset: Dataset = (globalForDataset.__dataset ??= seeded);

The two-PRNG rule

lib/procedural.ts and lib/data/seed.ts each carry a copy of the same mulberry32 generator. That duplication looks like a mistake and is not. The seed PRNG defines the dataset: product names, scores, review text and counts are all functions of its output sequence. Unifying the two would change every generated value and invalidate every number in this report, every screenshot, and every guard baseline.

A corollary: no Math.random() anywhere. Server and client must agree, so all procedural output is derived from a seeded PRNG or a hash.

A second corollary, learned the hard way in P2.1: a generated field that nothing renders is a field nobody has ever checked. Rng.logInt(0, n) passed Math.log(0) = -Infinity into the log-uniform roll, so every review's helpfulCount had been NaN since the baseline commit and the "sort by helpful" control had silently done nothing. Both were invisible for as long as no UI printed the number. When wiring an existing generated value into a surface, assert the rendered value is the right type — not merely that the field exists.

Append-only by construction

The moderation log has no delete or edit path. A queue that can be silently rewritten is not defensible when a vendor disputes a rejection, which is the entire reason the log exists alongside the status column. Keep it that way if you move it to a database.

Tokens are CSS custom properties in app/globals.css. Every colour carries a measured contrast ratio in a comment.

Selected tokens, with the reasoning that produced them
TokenValueWhy that value
--color-primary#2563ebThe single accent. Used for links, active states, primary buttons and the vendor-response block.

Rule learned the hard way

No grey lighter than --color-muted-foreground can reach 4.5:1. The three-step grey scale collapsed to two for text; hierarchy is now carried by size and weight instead of by colour. If you add a new grey for text, it will fail. Decorative glyphs may use the faint tone.

Accessibility posture

  • Target: WCAG 2.2 AA. 4.5:1 for text, 3:1 for graphics and control boundaries.
  • Verified contrast, not eyeballed. scripts/qa/contrast-audit.py computes ratios from relative luminance rather than trusting a designer's eye.
  • Keyboard and screen-reader paths come from Radix primitives; interactive controls carry real labels (lead status selects are labelled per contact, moderation buttons per target).
  • Reduced motion is honoured — the 3D hero renders statically and scroll reveals are suppressed.
  • Charts are hand-rolled SVG with accessible markup rather than canvas, so they can be labelled and read.
  • Every review has a stable anchor (id="review-<id>"), so a single review can be deep-linked and cited.

Tailwind v4 constraint

Tailwind v4 tree-shakes @theme tokens: a utility is emitted only if the scanned source contains the literal class string. A class built at runtime from a template will silently not exist. This is why lib/viz.ts holds literal class strings and why status-bar colour maps are written out in full. There is also no --duration-* theme namespace in v4.

The discipline that matters most

A guard that cannot fail is worse than no guard. Three guards in this project once passed on a false premise, because they asserted on static strings that the page already printed for other reasons — "Your response" also appears in the reply form's own label, so the check passed while the write went somewhere no page read. The fix was to post a unique marker and grep for that. Two real defects were found the moment the guards could go red.

Before trusting any new guard: break the feature on purpose and watch the guard go red.

What to run, and the environment traps that cost the most time.

npm install
npm run dev          # http://localhost:3000
npm run typecheck
npm run lint
NODE_OPTIONS= npm run build     # clear NODE_OPTIONS or the build can hang

Regenerating the knowledge graph

bash scripts/graphify-build.sh   # extract -> publish -> inline the viewer library

The published artifact (public/graphify/graph.json + graph.html) is committed, so a fresh clone ships with the graph; only graphify-out/ and the .venv-graphify/ virtualenv are ignored. The third pipeline step matters: graphify 0.9.61 emits vis-network as an external unpkg CDN tag, where the release that produced the original artifact inlined it. scripts/inline-graph-lib.mjs restores self-containment by substituting the pinned 9.1.6 build from scripts/vendor/. It is idempotent and fails loudly rather than shipping a half-inlined document. If graphify is ever upgraded, verify the served viewer still has zero external <script src> references — the failure mode is a blank canvas that looks identical to a successful build.

Environment gotchas

  • Never edit a shell script while it is executing. Bash reads a script progressively by byte offset, so an edit mid-run shifts the content under the interpreter and produces a spurious "syntax error near unexpected token" at a line that is perfectly valid. Re-run the unchanged script instead.
  • Space the QA guards ~13 s apart. POST /api/leads and POST /api/reviews carry a 5-per-60s limiter keyed on x-forwarded-for → x-real-ip → "unknown". Every guard sends none of those headers, so they all share one bucket; running the suite back-to-back returns 429 and reads exactly like a regression.
  • Clear NODE_OPTIONS for builds and browser QA. The sandbox injects a node shim that saturates and hangs child processes.
  • Never chain rm before a build. A delete guard blocks the rm, the && short-circuits, and you read a stale log and declare success.
  • Confirm the PID owning port 3000 before trusting a 200; a stale server serves old code.
  • Bash cd into the workspace fails intermittently (about 1 in 3). Retry in a loop.
  • Node cannot always see C:/... absolute paths here; prefer relative paths from the project root.
  • timeout N sh script.sh | tail does not bound a wedged browser run — an orphan holds the pipe open. Redirect to a file.
  • Browser automation wedges after roughly 8 to 11 page checks. Split matrices into runs of 2 to 3 routes. Route calls through scripts/qa/ab.sh.
  • WMIC is blocked, so leaked browser processes cannot be distinguished from the user's own. Kill none.

Code conventions that matter

  • React inserts a comment marker between interpolated text nodes. Any regex against rendered HTML must allow for it.
  • Never use Math.random(). Use the seeded PRNG so SSR and hydration agree.
  • Derive state during render, not setState in an effect. getSnapshot must be referentially stable in useSyncExternalStore.
  • A sticky element must be checked against what it duplicates. Do not repeat the same numbers at the same scroll position.
  • Do not hardcode what the framework appends — the root layout already adds the site suffix to every title.
  • Parallel edits to one file silently drop one. One file per message, then re-read.
  • formatPercent() scales by 100 (expects 0.64); formatPercentValue() does not. Mixing them produces figures like 1240%.
