00Five decisions I need before writing code

The prompt says not to ask permission for small implementation choices. These are not small — each one changes the shape of the whole program, and two of them contradict a decision you already made. Per your own standing instruction, I am flagging them rather than quietly choosing.

1 — This prompt supersedes "restraint by choice". Confirm the reading.

Project memory records the confirmed direction as "Light enterprise only… restraint by choice", and the earlier G2 benchmark document left this exact question open as Decision A — it was never actually answered.

This prompt answers it: §6 says the site "currently has a color problem" and authorises gradients, 3D, category colour systems and motion — while §5 still forbids dark/neon/glassmorphism.

My reading: the surface stays light; richness is added within light. Dark, neon and heavy glass stay dead. Is that right?

2 — All 3D must be procedural. This environment cannot generate 3D assets.

This product has no 3D-model generation and no video generation. Concretely that means:

  • No .glb/.gltf models — so GLTFJSX (repo 05) has nothing to convert. It is an asset-pipeline tool, not a renderer.
  • No .riv files — Rive (repo 10) is only useful once someone hand-authors animations in the Rive editor. The runtime alone renders nothing.
  • Theatre.js (repo 13) needs its Studio GUI for art direction. I cannot drive it.

So the 3D will be procedural R3F — spheres, nodes, instanced meshes, lines and shaders generated in code, deterministically positioned. That is exactly what §27 and §28 describe, so I believe it is the intent. Confirm?

3 — A hard bundle budget, or the performance achievement dies.

Current shipped JS is 1.3 MB. Installing the full 20-repo set would plausibly add 1.5–2 MB — roughly doubling it — and the existing 25/25 smoke and clean build are achievements worth protecting (§66).

Proposed rule: 3D, charts and heavy motion are always dynamically imported and client-only, so they never enter the initial route bundle; initial JS stays ≤ 1.5 MB. Agreed, or do you want a different ceiling?

4 — This re-orders the report you just approved.

FUNCTIONALITY_AND_UI_REPORT.html — published an hour ago and named the source of truth by §1 — lists 10 P0 items (Postgres, Auth, RLS, vendor isolation, audit logs…). §21 of this prompt says to do the visual system first and defer backend.

Those two documents now disagree on sequencing. I will follow the prompt (UI first) and mark the backend P0 list as deferred — confirm you want that inversion.

5 — I recommend not installing the seven MCP servers.

Your MCP config is empty ({"mcpServers": {}}). I checked each of the seven requested servers against what is already available — the honest answer is that they add configuration surface and auth risk for near-zero capability gain (full table in §05).

I will do this work with built-in tools plus the agent-browser CLI, which already covers Playwright's role. Say the word if you want Playwright MCP installed anyway — it is the only one with a real case.

The bundle rule that makes this safe

Every one of those except motion is dynamically imported and client-only, loaded only when its component enters the viewport. Three.js and Recharts must never appear in the initial route bundle — that is what keeps the 1.3 MB baseline from doubling.

Two honest limitations

GSAP licensing needs checking before ship — it is free for most use, but ScrollTrigger's terms changed when Webflow acquired it. I will verify before adopting rather than assume.

No generated imagery. §31 asks for real product screenshots. I cannot produce or source licensed product photography. What I can do is generate abstract, deterministic, code-drawn product visuals — which §31 explicitly allows as the fallback — and wire the next/image path so real assets drop in later.

07Proposed first implementation task

W1 · Design token expansion — no component changes

Extend app/globals.css with the visual token layer: a controlled data-visualisation palette (cyan / violet / emerald / amber / rose, non-interactive), gradient tokens, motion duration + easing tokens, chart series tokens, 3D material tokens, and a per-pillar category colour map. Then verify every new text pairing against WCAG 2.2 AA and confirm the built CSS actually emits each token.

Why this first. It is the smallest possible change with the largest downstream leverage: every later wave reads from it, it touches no component and no route, it cannot regress the 25/25 smoke, and it is the one thing the current system genuinely lacks — the report already established that the tokens exist but nothing is spending them. It also directly answers §25, "the current interface is too visually restrained", without committing to a single 3D decision that the five questions above might change.

Exit criteria: new tokens present in the built CSS · contrast re-audited at 16/16 or better · tsc 0 · eslint 0 · build green · smoke 25/25 · a screenshot diff showing no unintended visual regression.
